# kagiboy cartridge firmware (RP2350)

MIT. Work in progress: the board isn't built yet.

| Crate | What | Status |
|---|---|---|
| `core/` (`kagiboy-core`) | The wallet logic: the Game Boy mailbox, PIN and wipe rules, BIP-39 words, Solana and EVM keys, transaction decoding and signing, swaps, pairing, QR codes; the bus-side mailbox (`bus.rs`) and the stored-wallet format (`persist.rs`). `no_std`, so the same code runs on the RP2350 and in host tests | done, matches the browser chip byte for byte |
| `cart/` (`kagiboy-cart`) | The firmware for the board in `hardware/cart` (Embassy, RP2350B at 150 MHz): serves the wallet ROM and the mailbox on the Game Boy bus with PIO + DMA, runs `kagiboy-core` with the keys in the SE050 | bus, mailbox, wallet, SE050 and the phone link (ESP32-C3 on SPI0) done, builds; LIS3DH next |

## How the bus is served (`cart/`)
- `gb_read` (PIO0 SM0) answers every ROM read from a 32 KB image in SRAM: two chained DMA channels turn the address it
  pushes into the byte at that address and hand it back, and it drives D0-D7 in time. The chip's half of the
  mailbox sits in that image at 0x7F00, where the hardware build of the ROM reads it.
- `gb_write` (PIO0 SM1) samples every write cycle. The board has no /WR line, so a write is a cycle with /RD high; a
  third DMA channel streams the samples into a 32 KB ring, so nothing is lost while the CPU signs or writes flash.
- The CPU drains the ring into the Game Boy's half of the mailbox and runs the wallet.
- `cart/pio/*.pio` are generated by `hardware/sim/emit-pio.ts` from the cycle-level simulation's own design, which
  passes on the real ROM's bus traffic with this board's pin map (83 ns of margin to the early latch at 150 MHz,
  0 contention, hold or write errors; see `docs/hardware-sim.md`). Two independent assemblers (pio-parser, which the
  firmware uses, and Adafruit's pioasm) give identical instruction words.

## Keys and PIN in the SE050 (`core/src/se050.rs`, `core/src/vault.rs`)
- **At SET_PIN:**
  - the two account keys are imported into the SE050: Ed25519 for Solana, secp256k1 for EVM;
  - the PIN becomes an SE050 UserID object with a 5-attempt limit;
  - the recovery words aren't kept anywhere.
- **Policies:** a key signs only inside a session opened with that PIN. Everyone else may only read the public key
  or delete it, so a locked-out cartridge can still be wiped.
- **The PIN on the wire:** the UserID value is 16 bytes of SHA-256 over a per-wallet salt and the digits, so the
  digits never cross the I2C bus.
- **Two counters, two jobs:**
  - The SE050 doesn't report UserID failures, so the firmware keeps the browser chip's counter in flash (a try is
    spent before the check, and five failures wipe). That counter drives the screen.
  - The SE050 enforces its own limit of 5 regardless. Firmware that reset its counter still couldn't guess further.
- **What the flash record holds:** the salt, the try counter, the pairing and the public keys. No secret.
- **ECDSA:** the SE050 signs with a random nonce and may return a high S. The firmware normalises to low S and
  finds the parity by recovering its own address.
- **Ed25519:** the SE050 wants public keys and returns r and s byte-reversed (AN12413 chapter 7).
- **The driver** is written from AN12413 (APDUs) and NXP's Plug & Trust middleware (T=1 framing, CRC, read
  polling, BSD-3-Clause), not linked to either. Nitrokey's `se05x` crate wasn't used: it's LGPL-3.0, which doesn't
  fit MIT firmware that's statically linked.
- **How it's tested** without a chip (`core/tests/se050.rs`, `core/tests/se050_model/`):
  - A behavioural SE050 model: T=1 with busy NACKs, WTX, chained blocks and damaged frames, plus the applet subset
    with real cryptography, AN12413's policy rules and the attempt limit.
  - All recorded browser sessions replay through `Se050Vault` and the model byte for byte, also with a difficult
    SE050 (busy, WTX on every response, 16-byte response blocks).
  - Further tests: no secret in the store, no signing without the PIN session, five wrong PINs wipe, the SE050's
    own limit holds, recovery from a damaged frame, a 600-byte chained command.
  - Frame CRCs are checked against NXP's own CRC code.
  - Planted bugs (Ed25519 byte order, S normalisation, a permissive policy, signing outside the session) are all
    caught.

## The phone link (`core/src/phone.rs`, `core/src/link.rs`)
The phone's messages arrive over Bluetooth at the ESP32-C3 (`firmware/esp32c3`), which offers them on SPI0. The
cartridge polls every millisecond (`link::LinkMaster`, the WiFi cart's SPI framing with the direction reversed) and
`phone::PhoneServer` answers them with the chip. Spec and tests: [docs/phone-link.md](../../docs/phone-link.md).
- `tests/phone_link.rs`: the web app's bytes for every phone call of the recorded sessions, and the reference
  server's replies: identical, with the software vault and with the SE050 behind the Game Boy bus.
- `tests/spi_link.rs`: the same sessions through both link halves as they ship. The ESP's C half is built with the
  host compiler and driven over a pipe. The link gets damaged and missed transfers and restarts on both sides.
  Planted bugs in either half are caught: no duplicate filter, no ack, no CRC, an ack crossing an ESP restart, a
  resent reply passed on twice.

## The browser chip is the reference
`web/src/chip/chip.ts` is the chip the ROM is developed and tested against. `kagiboy-core` is its port, and is held to it:
- `web/scripts/chip-vectors.ts` drives the browser chip through full sessions and records every mailbox reply,
  every phone-side refusal, every pairing code and every signature, with a seeded random stream and a fixed clock
  (`core/tests/vectors/*.json`).
- `core/tests/vectors.rs` replays them against the Rust chip with the same random bytes and requires identical
  bytes: replies, the chip's half of the mailbox after every command, refusal texts, signed transactions.
- The networks, swap tokens and fees are generated from the TypeScript tables (`web/scripts/chip-tables.ts` ->
  `core/src/tables.rs`), so the two can't drift.

Run (from `web/`, then here):
```sh
pnpm exec tsx scripts/chip-vectors.ts ../firmware/rp2350/core/tests/vectors
pnpm exec tsx scripts/chip-tables.ts
cd ../firmware/rp2350 && cargo test -p kagiboy-core --release
cargo build -p kagiboy-core --release --target thumbv8m.main-none-eabihf
cd cart && cargo build --release        # the firmware; needs rom/build/wallet-hw.gb (make hw in rom/)
```

Differences from the browser chip, by design:
- Time comes from the phone (the cartridge has no clock): the 60 s pairing lapse and swap deadlines use it.
- Keys are derived on the chip as in the browser; on the cartridge they will move into the SE050 (next step).
